# Introduction 

In this example, we will write a systems-level, automated black-box tests for
the Pitt website using the Playwright framework.  Specifically, we are going to
test the URL:

https://www.pitt.edu/

# Prerequisites

1. Please install the [Node.js JavaScript runtime environment](https://nodejs.org/en/download).

1. Please install the [Playwright Test for VSCode extension](https://marketplace.visualstudio.com/items?itemName=ms-playwright.playwright).

1. Please install Playwright after opening the folder in VSCode.  You dan either in VSCode go to View > Command Palette > Test: Install Playwright, or you can execute the following commandline on your shell:
   ```
   npm install -D @playwright/test
   ```

   Then install the chromium browser as our test target:

   ```
   npx -y playwright install --with-deps chromium firefox webkit
   ```

### Tips for selecting the best locator string

When using the Playwright locator selector tool, it generates a code snippet
that returns a locator object using built-in locator APIs, that can uniquely
identify that element.  Only if it is infeasible to use built-in locator APIs
will it use the locator() API with an XPath or CSS selector.  It will always
try to use built-in locator APIs first before resorting to XPath or CSS
selector, because it usually results in more robust tests that do not break due
to small changes in the DOM.  That is because built-in locator APIs work on the
Accessibility Tree which is another abstraction layer above the DOM that only
shows elements that are accessible to the end user (minus the numerous \<div\>
elements in the DOM that apply CSS styling).  The Accessbility Tree is also
what the screen reader accesses when it reads out the web page for visually
impaired users, so it only contains components meaningful to the user.  So
changes to the DOM (e.g. inserting or deleting \<div\> elements) that do not
change user functionality will not change the Accessibility Tree.

The Accessibility Tree can be viewed in the Chrome web browser by right
clicking on any element in the web page and then choosing 'Inspect', and then
on the Dev Tools pane that gets launched on the right, selecting the
'Accessibility' tab and turning on 'Show accessibility tree'.  Alternatively,
you can open the
[tests/pittedu.spec.ts-snapshots/TEST-8-ARIA-SNAPSHOT-1.aria.yml](tests/pittedu.spec.ts-snapshots/TEST-8-ARIA-SNAPSHOT-1.aria.yml)
file that contains the ARIA (Accessible Rich Internet Applications) snapshot of
the www.pitt.edu main page, which is a more concise form of the Accessibility
Tree (it was generated by running TEST-8).  This ARIA snapshot is what the
Playwright built-in APIs see.

Long CSS or XPath chains below are an example of a bad practice that leads to
fragile tests:

```
await page.locator(
    '#tsf > div:nth-child(2) > div.A8SBwf > div.RNNXgb > div > div.a4bIc > input'
).click();

await page.locator(
    '//*[@id="tsf"]/div[2]/div[1]/div[1]/div/div[2]/input'
).click();
```

Instead, better to try to come up with a in locator that is close to how the
user perceives the page using built-in APIs such as getByRole(), while being
close to the spirit of the test step.  You will have to peruse the
[Locators](https://playwright.dev/docs/locators) tutorial mentioned previously
to understand what built-in locators are available.

One problem when using the Playwright locator selector tool is that it does not
know the context of the test scenario so it may sometimes suggest a locator
that is divorced from the scenario, in which case you will have to tweak it
yourself.  For example, the same list item can be located using its relative
position in the list (e.g. 3rd place) or it can be located using the text in
the list item.  Which is appropriate depends on the actual test step in the
scenario you are trying to automate.

# Task 3: Run test cases

When you are done writing your tests, you can either run them on the VSCode
Testing extension (th Flask icon menu) or you can run them on the commandline
using the following:

```
npx playwright test --project=chromium
```

If all goes well, then it will show all 7 tests passing:

```
> npx playwright test --project=chromium

Running 7 tests using 7 workers
  7 passed (5.2s)

To open last HTML report run:

  npx playwright show-report
```

Running the show-report comamnd as above will open a browser tab with detailed
test results.  Now, the above command only runs your tests on the chromium
browser for brevity, but if you wanted to be rigorous, you can omit the
--project argument:

```
npx playwright test
```

Which will run the 7 test cases in each of the 3 browsers configured: chromium,
firefox, and webkit.  

```
> npx playwright test

Running 18 tests using 12 workers
  18 passed (27.1s)

To open last HTML report run:

  npx playwright show-report
```

Also, by default Playwright runs tests in headless mode, as in the browser is
not displayed.  This is done 1) to speed up testing and 2) because often tests
are run on machines with no display such as cloud machines running CI/CD
pipelines.  If you want to see the browser running, you need to add --headed:

```
npx playwright test --headed
```
